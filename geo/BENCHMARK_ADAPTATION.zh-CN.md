# 从 GEO-Bench 与 AutoGEO 借鉴什么

**原论文：** [GEO: Generative Engine Optimization（v3）](https://arxiv.org/html/2311.09735v3)；[What Generative Search Engines Like and How to Optimize Web Content Cooperatively（AutoGEO，v1）](https://arxiv.org/html/2510.11438v1)。本文把两篇论文的实验思想用于 EAU 的测试设计，不把论文报告的平均提升视为 EAU 的预期提升。

## 1. 两篇论文测量了什么

| 维度 | GEO-Bench | AutoGEO | EAU 当前缺口 |
| --- | --- | --- | --- |
| 候选来源 | 每个问题固定取前 5 个来源，改写其中一个文档 | 每个问题配 5 个候选文档；用多种 LLM 构建生成引擎 | 当前项目 URL 在 GPT/Codex 工具返回中 0/4；还没有进入可评估“项目页被引用多少”的阶段 |
| 曝光指标 | 被引用句子的归一化词数、按位置衰减的词数，以及主观印象 | 沿用 Word / Pos / Overall，并分析不同引擎与领域 | 现有项目页召回、提及、引用主要是二值；缺答案级的引用份额与位置 |
| 生成方法 | 分别测试可信来源引用、可核实统计、引文、流畅度等；关键词堆砌效果差 | 从高低可见文档对抽取偏好规则，再用规则指导改写 | 现在没有足够的同平台完整答案与文档对，不能声称已学到“GPT 偏好规则” |
| 质量约束 | 重点测内容可见度 | 同时测关键点召回/矛盾、引文支持、清晰度与洞察 | 需要防止为了曝光改写 EAU 的科研事实或制造引文 |

两篇论文的主要生成阶段实验控制了候选文档集合，因此适合回答“**来源已经被取回时**，内容怎样影响答案”。EAU 项目页当前的首要问题还包括真实搜索系统是否能发现和取回项目 URL。两关必须分开报告。GEO-Bench 使用多种查询并重复采样；AutoGEO 还测试不同引擎、领域与低可见文档，提示我们保留跨平台和留出问题的结果。

## 2. EAU 的两关实验

### 关 A：真实检索与引用

用真实平台的新会话，保存来源列表、最终答案、时间和搜索设置。对项目页、论文页、仓库 URL 分别记录出现次数；再记录项目页是否在最终答案中被引用。现有证据仅为本会话 GPT/Codex 网页搜索工具的 4 条查询：项目 URL **0/4**、论文 URL **4/4**、仓库 URL **0/4**。没有稳定的 top-10 排名，也没有这 4 次查询对应的独立最终答案。

**门槛：**项目页未进入候选来源时，项目页的答案级 Word/Pos/Overall 记为**不适用**，不是 0 分改写失败。优先核实论文页到项目页的链接，并在改动后重新测真实召回。GitHub README 与项目页内容候选可继续准备，但不能凭本地代理分数宣布曝光收益。

### 关 B：固定候选来源下的内容实验

把同一组来源和同一个问题固定，分别替换 EAU 项目页的一个候选版本，让相同生成引擎重复回答。这样才能较干净地比较节点内部的写法。候选方案应各占一条实验臂，与原页对照：

1. **来源明确的研究摘要：**方法主张后给出论文或原始结果的可核对链接。
2. **可核实的数字与条件：**仅使用论文中有出处的任务、基线、结果和适用条件；不增加无来源数字。
3. **清晰的问题式摘要：**让“EAU 解决什么、与 SEAL/GenEnv 有何差异”可以直接从可抓取正文回答。
4. **负对照：**关键词堆砌或仅增加重复术语；预期不作为正式优化方案，只用于确认本地评分器不会奖励重复文本。

上述都是**待测候选**，不是已实施改动。每臂保持相同的检索来源、模型、提示和问题；换新会话并至少重复 3 次。训练/挑选候选使用开发集，最终报告使用预注册留出集，避免反复针对 Q1–Q4 调词。待测问题见 [查询库](benchmark-query-bank.json)。

## 3. 新增的答案级指标

仅在保存了完整答案与逐句引用后计算：

| 指标 | EAU 记录口径 | 为空时的含义 |
| --- | --- | --- |
| 项目页引用份额（Word 类比） | 引用项目 URL 的句子所占答案字数比例；多来源共引的句子按来源数均分 | 没有完整答案或引用映射，留空 |
| 首次项目页引用位置 | 项目 URL 首次被引用的句序 / 答案句数 | 没有项目引用时记为“不适用”，不要填 0 |
| 位置加权份额（Pos 类比） | 对引用项目 URL 的句子按出现位置递减加权，再按答案总字数归一化 | 缺逐句引用则留空 |
| 引用支持率 | 被引用句中，引用 URL 真正支持对应 EAU 事实的比例 | 需人工复核或可审计的评审记录 |
| 关键点保真 / 矛盾 | 预注册 EAU 方法和结果的关键点是否保留、是否出现与论文矛盾的表述 | 没有参考关键点或完整答案则留空 |

中文与英文可分别用字符数与词数；跨语言不直接比较绝对份额。`Word`/`Pos` 是**借鉴的 EAU 操作化指标**，不能直接称为论文原基准分数。若将来有原始逐句引用数据，再决定是否实现精确复现。

## 4. 自动提取偏好规则的前提

AutoGEO 从同一查询的高/低可见文档对解释差异、抽取洞见、合并并过滤规则。EAU 可以借鉴这个顺序，但需要先积累**同平台、同查询、完整答案与引用映射**。目前只有返回 URL；样本不够，不能从“论文 4/4、项目页 0/4”推断模型偏好某种写法。

未来规则卡至少包含：平台/模型、问题类别、文档对、完整答案证据、抽取出的规则、反例、留出集复测结果。不同平台规则分别保存；只有在留出查询上重复有效，才考虑跨平台迁移。任何规则都受“科研事实准确、引用可核验、无矛盾”约束。

## 5. 对现有 wrapper 的具体调整顺序

1. **现在：**继续把 `geo-explore` 的真实来源树作为入口发现线索；项目页 0/4、论文 4/4，先核实论文→项目页边。真实效果仍未测。
2. **有完整答案后：**为 `geo-compare` 增加上述答案级连续指标的独立报表，保留现有二值召回/提及/引用报表。缺值继续保持未知。
3. **有足够文档对后：**把 AutoGEO 式规则发现作为候选生成器，输出可审查的规则与证据，不让规则生成器直接决定上线。
4. **候选上线前后：**本地固定来源实验只用于筛选内容写法；真实平台的配对召回、引用和质量结果用于判断是否真的改善。跨平台退化继续作为拒绝条件。

当前没有新增真实平台观测，所以本文没有给任何候选填写曝光提升。
